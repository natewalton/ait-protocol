# Independent design review

Verdict: BLOCK pending the five narrow corrections below. The principal/target/visibility/lifecycle separation is sound; it does not need a new registry, resolver mode, or retry supervisor.

Reviewed 2026-11-09 against installed source `98a7de6f04573044e5eb0c3d75a5390e1072d9f1`, complete proposal and audit, target AGENTS/development instructions, and delivery-coordination/general-systems/spec-design skills. This is a design review, not implemented-fix validation. No authentication, live writes, rebuilds, restarts, or test invocations were performed. Source locators below are relative to the installed target.

## Blocking corrections

1. **Readiness must govern authoritative name answers, not just the health probe.** `server.ts:127-130` resolves directly against the projection; `queries/resolveHandle.ts:19-34` returns one indexed match or absence without knowing whether initial local backfill completed. `peerFeed.mjs:90-106,136-145` builds that projection asynchronously. Merely changing `/xrpc/_health` leaves a cold or terminally failed partial local projection able to report a false definitive negative or a unique result before a local namesake is imported. `mcp/src/atproto/actorLookup.ts:35-40` treats HandleNotFound as authoritative absence; `mcp/src/atproto/mentions.ts:47-55` then permits a post without the intended mention. Specify a projection-unavailable error for name resolution while local indexing is starting/failed, including public server callers that bypass the identity endpoint. Explicit DID identification and readable retained history need separate treatment. Do not require optional peer backfill or connection before local readiness: uniqueness is over indexed accounts, and offline peers must not hold local work hostage. Add delayed/failed local backfill tests through both public resolution and a real mention/action consumer, asserting no false absence or early target selection.

2. **The picker cannot choose the correct DID syntax with its existing token contract.** `mcp/src/aitty/interactive.ts:195-219` emits `withAt: true` both for post/reply mentions and for `follow @alice`, `retire @alice`, etc. `picker.ts:39-44,240-247` receives no other context. Mapping withAt directly to `@{did:...}` breaks prefixed command arguments: `normalizeActor` removes only `@`, leaving `{did:...}`, which is neither a DID nor a valid handle. The proposal's desired distinction is right, but its file list omits the caller that must provide that distinction. Add `interactive.ts` and a minimal token insertion-context distinction (or equivalent existing-context solution). Test actual finder -> picker -> command/mention parsing for `follow alice`, `follow @alice`, `retire @alice`, `post @alice`, and `reply ... @alice`, not only manually constructed picker tokens.

3. **Peer lifecycle data currently stops before the promised CLI consumer.** `peerNetwork.mjs:314-316` supplies the status JSON, but `peerCli.mjs:28-30,55-56` prints only transport state, name, and key. `bin/status.sh:84-86` delegates peer output to that renderer. Adding feed fields in the network/client leaves `ait status` hiding importer failure and saved-attachment diagnostics. Add `appview/src/peerCli.mjs` to C, specify its displayed feed state/error and unavailable-attachment reason, and assert literal `ait status` output with Linked transport plus failed importer and with retained approval plus incompatible relay.

4. **“Resolve before namespace changes” is insufficient for crash-safe exact-handle migration.** Existing `peerPrepare.mjs:140-160` updates account handles before its final env commit (`:175-186`). The proposal requires capturing an old exact custom/full handle before that operation, but does not require durably writing its DID first. If the capture remains in memory and preparation crashes after the handle change, the next attempt cannot resolve the old exact handle under the proposed exact-match rule. The rollback copy alone is not a recovery path if restoring its old handle no longer matches the account. Require the atomic, preconditioned operator DID env commit to complete before any namespace mutation that can invalidate its reference; failure must stop before those mutations. A successful DID conversion can safely remain if subsequent namespace work fails. Specify rollback as restoring configuration only while its reference is still valid, or use the captured DID after namespace changes. Add failure injection immediately after first account rename and retry from disk.

5. **The explicit managed-port limitation promises a help change with no help file in scope.** Public `ait help start` is authored in `ait:112-123`, not the listed documentation files. The proposal explicitly promises corrected help, yet omits `ait`. Add it (or identify the actual supported help surface being changed) and test the public help plus prelaunch rejection with zero process launches. With `interactive.ts`, `peerCli.mjs`, and `ait` added, the current 22-file list becomes 25 distinct files (16 production, 6 tests, 3 docs/examples), unless another listed file is removed. Recount rather than retaining the current total.

## Acceptance details to make explicit while revising

- Define the health body and CLI mapping sufficiently to distinguish starting from terminal failure although both use HTTP 503. `status.sh:15-21` currently uses curl -f, discarding that distinction. Both newly launched and adopted AppViews must wait correctly; `start-all.sh:143-154` currently skips the wait for an adopted service. Terminal failure returns nonzero; starting reports progress and can be cancelled. Do not manufacture failure from a quiet feed or add an arbitrary feed-age timeout. Upstream reconnect may continue while starting; caller cancellation/dependency terminal failure must still be observable.
- A multi-target watch must resolve every requested reference before creating any follows if the stated “ambiguity aborts before ... writing” guarantee is literal. `mcp/src/aitty/main.ts:272-300` currently interleaves resolution and writes. Test [valid new target, ambiguous target] in that order; a one-target ambiguity test misses this. This needs no new storage or rollback mechanism: separate resolution from execution within the existing function.
- Keep the optional attachment catch scoped to a known peer and clean only resources acquired by that attachment; retain fatal control socket/local identity/ownership errors. State how a failed attachment's diagnostic remains available when no `sources` entry exists. Existing `attach` creates listener/client before registration (`peerNetwork.mjs:242-264`); existing overall cleanup is reachable only after full startup (`:380-389`). Test failure before and after each acquisition, plus cancellation/initial HTTP listen failure. No blanket catch around `startPeerNetwork` is acceptable.

## Systems and scope assessment

The code shows five distinct concepts: authenticated principal (`viewer`, local resolver), configured operator (`OPERATOR`), submitted reference (`resolveActor`/`resolveActorToDid`), projection visibility (`retiredOnly`), and feed/transport lifecycle (`running`, subscription promise, connection paths). Operator binding generalizes the existing env principal instead of inventing role state. Feed status exposes a real lifecycle rather than adding a supervisor. Existing consumer exceptions to remove are directory-based bare selection (`handles.ts:34-59`), saved dotted-reference fallback (`main.ts:281-285`), result-count-based picker rewriting (`picker.ts:244-246`), and projection-based operator authority (`server.ts:238-240,383-389`). These four source-grounded policies are precisely where the model is interleaved.

A, B, and C each reach a real consumer and can remain separately deliverable. A is the smallest restoration of operator service. The complete proposal is broader than that restoration, but its other two slices address demonstrated user failures and need not be dropped merely to meet a file threshold. Do not describe the entire 25-file repair as one simple feature or make A wait on C. The new binder should remain operator-specific; all action targets should retain one shared resolver meaning. No evidence in this review supports changing JWT issuer trust, deleting valid namesakes, automatic terminal retries, or arbitrary port configuration support.

The baseline green checks are not evidence of delivery. The corrected acceptance must exercise the real token finder, public resolution under unavailable projection, crash/retry from disk, and rendered peer status. Once those corrections are incorporated, the architecture can be ready for implementation review; this report grants no implementation, deployment, branch switch, or live-restart approval.

## Re-review, 2026-11-09

Verdict: GO for the revised proposal only. The original BLOCK above is preserved as the first-round result. No residual design blocker was found after reading the complete revised proposal and self-review and rechecking the relevant installed source at unchanged `98a7de6f04573044e5eb0c3d75a5390e1072d9f1`.

The revision closes the five findings as behavior contracts, rather than merely adding named components:

- It rejects authoritative name answers while the local projection is unavailable at every public name boundary, explicitly including direct feed/profile/record callers. Rechecked `server.ts:127-134,165-190,227` and `queries/getRecord.ts:20-23`: the implementation can enforce this at the HTTP boundary without giving the generic resolver a new local-only mode or preventing explicit DID/URI history reads. Optional peer progress remains independent from local readiness.
- It replaces the conflated picker token distinction with insertion context supplied by the actual interactive caller, and tests caller -> picker -> parser for prefixed arguments and mentions. This addresses `interactive.ts:195-219` and `picker.ts:39-44,240-247`; the new context replaces the old representation instead of accumulating flags.
- It reaches the terminal peer-status consumer through `peerCli.mjs`, preserves a failed attachment diagnostic before a client exists, and tests rendered `ait status` output. Its runtime record is scoped to the existing approved-peer owner and is not another persisted trust registry.
- It commits the stable operator DID before namespace mutations, refuses to rename after a failed env commit, preserves that DID across later preparation failure, and distinguishes rollback before versus after rename. This resolves the disk-only retry failure possible with current `peerPrepare.mjs:140-160,175-186` ordering.
- It includes public `ait help start` and counts 25 distinct files: 16 production, 6 tests, 3 docs/examples. The managed restriction now covers the effective ports of all three services, consistent with rechecked PLC launcher `:17-18`, PDS launcher `:17-25`, their shell wrappers, and the fixed discovery ports. It keeps direct fixture startup available on ephemeral ports.

The additional acceptance requirements also close: distinct health bodies for starting versus terminal failure; adopted AppViews use the same readiness wait; watch resolves all targets before follow creation; and partial optional attachment cleanup retains diagnostics without masking fatal local ownership/identity errors. These changes preserve three independently useful slices and do not make A wait on B/C. Baseline green tests still carry no implemented-fix claim.

Residual implementation risks, not unresolved design blockers:

1. Exercise every direct name boundary, especially getRecord and retirement; an identity-endpoint-only guard would fail the revised contract. Validate explicit DID syntax without unnecessarily gating retained-history reads.
2. Ensure read-only operator binding and maintenance agree on the actual account store and dotenv precedence; test duplicate/exported assignments, atomic failure, and disk-only retry after rename. A read/compare immediately before rename is a precondition, not a general cross-process locking guarantee; the existing stopped-service maintenance boundary remains essential.
3. Preserve feed error identity and cancellation when replacing the currently swallowed promises; do not classify unexpected normal completion as healthy, confuse reconnect with terminal failure, or leave initial-listen/partial-attachment resources live.
4. Keep startup wait ownership checks intact for adopted processes and test effective inherited-versus-file port precedence without exposing secrets. The updater's existing partial-service rejection (`bin/update.sh:71-79`) remains an intentional recovery gate, not a reason to silently restart an unhealthy installation.
5. Run the stated isolated consumer journeys and independent authorization/persisted-write review before any delivery claim. This GO is permission to treat the design as ready for implementation planning, not evidence that implementation passes or authorization for deployment, release, branch switching, or restarting installed services.
